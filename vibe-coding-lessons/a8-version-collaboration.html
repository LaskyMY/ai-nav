提交、版本、协作

代码写完了不代表结束了——要让团队用上、不影响别人、出问题能回退。 最后一天，小K 走通版本控制的全流程，把工具真正"交出去"。

📚 课程目录
SCENE 9 · 第十天上午

小K： "G哥，工具做好了，在编辑器里能跑。我怎么给其他人用？把代码文件夹压缩发群里？"

G 哥（捏了捏眉心）： "绝对不能。第一，压缩包没有版本历史， 出了问题不知道是你改的还是别人改的。 第二，你这压缩包和服务器上 P4 仓库里的版本完全脱节， 同事拿到了也没法跟他的代码合并。"

G 哥： "今天教你走一遍 P4 的完整流程——Checkout → 改代码 → 编译验证 → Submit。 顺便讲讲 Shelve 是干嘛的、为什么 Code Review 之前要先 Shelve 一下。 你走通了这个流程，才算真正'入行'了。"

为什么要懂这个

代码写完了，只完成了 50%。剩下的 50% 是让团队安全地拿到你的代码。 版本控制是多人协作的基础设施——它不是你"顺便学"的东西， 是你"入行必须会"的东西。

很多新人把"改代码"当成主要工作，把"提交"当成一键操作。 实际上，在 UE 大项目里，错一次提交可以让全组编译不了、让美术打不开编辑器。 把提交流程走对，是对团队的基本尊重。

为什么 UE 大项目用 Perforce 而不是 Git？

为什么要懂这个

不是 Git 不好——是 UE 项目有大量几百 MB 的二进制文件（贴图、模型）， Git 天生不适合存这些。

简单记住两点：

  • Git 是为纯代码（文本文件）设计的。 它存每一个版本的完整快照，一个 200MB 的贴图改了 10 次， Git 仓库可能膨胀到几个 GB。
  • Perforce 是为代码+大型二进制资产设计的。 它的服务器集中式管理，二进制文件只存差异，对大型资产友好得多。

UE 项目就是典型的"几万个小文本代码文件 + 几千个大型二进制资产文件"—— P4 正好是为此设计的。在游戏行业，P4 是事实标准。

Perforce 五个核心操作，记一辈子

① Sync — "把服务器上最新的拉下来"

每天开工第一件事：P4 Sync。把同事提交的最新代码同步到你的 Workspace 里。 就像打开共享文件夹，先检查有没有新文件。

关键：Sync 不会覆盖你正在修改的文件。它只更新你没在修改的文件。 如果你改着的文件和同事的提交冲突了，P4 会让你手动处理——而不是悄悄覆盖。

② Checkout — "我要改这个文件了"

P4 管理的文件默认是只读的。你要改它，必须先 Checkout。 这个动作不是多余的——它告诉 P4（和团队）："这个文件现在归我管了， 我正在动它。"其他同事在同一时间也可以 Checkout 同一个文件， 但提交的时候 P4 会帮忙处理合并。

⚠️ 千万别做的事

没 Checkout 就强行改了文件（比如手动把只读属性去掉）——然后发现改完了存不了。 P4 不认你这个修改，因为它在服务器端没看到"你声明了要改"。

流程必须遵守：先 Checkout，再改代码。

③ 改代码 + 编译验证

这一步你已经会了——Day 8 完整走过。在本地写代码、编译、跑起来验证。 确认功能正常、没有新引入的编译错误。

④ Shelve — "存到服务器但不提交"

为什么要懂这个

Shelve 是新人最容易忽略的操作——但它解决了一个核心矛盾： 你代码还没准备好正式提交，但需要给别人看、或者想存个安全备份。

Shelve 的作用：把你的改动上传到 P4 服务器， 但不合并到主分支。相当于"把草稿存到云端，但不发表"。

什么时候用 Shelve：

  • Code Review 之前——把改动 Shelve 到服务器， 告诉 G哥 "CL #12345，帮我 review 一下"。 G哥 能直接在你的 Shelve 上看到每一行改动。
  • 代码写到一半要下班了——Shelve 到服务器， 万一明天你电脑坏了，代码还在 P4 上。
  • 需要换一台电脑继续写——Shelve → 到另一台电脑上 Unshelve → 继续写。

⑤ Submit — "正式入库"

代码经过你自己验证、经过 Code Review（如果团队有要求）， 就可以 Submit 了。Submit 之后，你的改动就正式进了 P4 仓库， 其他同事 Sync 的时候就会拿到你的代码。

Submit 的时候要写一段描述（Description），说明你改了什么、为什么改。 这不是形式——三个月后你回来看这个提交，描述写得好能让你 10 秒想起来上下文； 描述写了 "fix" 一个字，你得重新读全部 diff。

🔑 一个好 Description 的样子

❌ 不好的描述："修了一下"、"update"、"Fix bug"

✅ 好的描述："修复编辑器启动时 MyTool 插件加载失败的问题。 原因是 Build.cs 里漏了 Slate 依赖。加了依赖，并加了一个空指针检查。"

好的描述包含三要素：做了什么 + 为什么做 + 怎么做的。

Code Review —— 代码给别人看一眼再入库

为什么要懂这个

很多新人把 Code Review 当"被检查作业"——觉得紧张。其实 Code Review 是新人成长最快的方式：一个有经验的人花 10 分钟看你的代码， 指出的问题够你自己摸索一周。

Code Review 的流程通常是：

  1. 你把代码 Shelve 到 P4，拿到一个 CL 号
  2. 把 CL 号发给 G哥（或团队指定的 Reviewer）
  3. Reviewer 在 P4 里看你的 Shelve，逐行看改了啥
  4. 如果没问题——Reviewer 说 OK，你可以 Submit
  5. 如果有问题——Reviewer 在具体行上写评论，你改完再 Shelve，再 Review，直到通过

不要把 Review 的意见当成"批评"。 每一条 Review 意见都是一个老手在告诉你"这里可以写得更好"—— 这恰好是自学最难获得的东西。

一个完整的工作日流程

把今天的内容串起来——你今后每天的典型节奏：

  1. 早上到工位：P4 Sync，拿到同事的最新代码
  2. 改代码之前：P4 Checkout 你要改的那些文件
  3. 写代码 + 编译 + 本地验证
  4. 改完了、验证过了：P4 Shelve（如果需要 Review）
  5. Review 通过后：P4 Submit，写清楚描述
  6. 下班前再做一次 P4 Sync，保证明天开工的时候代码是最新的
写代码让你成为一个"能做出东西的人"。
会提交流程让你成为一个"能跟团队协作的人"。
两样齐全，你才是一个完整的开发者。
