读懂报错

小K（截图发了三张到群里，打了八个感叹号）： "G哥！！！！编辑器崩了！！！！！是不是我把引擎搞坏了"

G 哥（点开第一张截图，看了一眼）： "没崩，这是编译报错。你看看第三行——它告诉你是哪个文件的第几行出了问题。 你那个文件第 47 行少了个分号。"

小K："…………就这？？？那后面为什么还跟着 200 行红字"

G 哥： "因为编译器在'补刀'。一个分号少了，后面整段代码的语法全乱了， 编译器把每个后续的异常都报了一遍。但关键信息永远在第一条报错。 今天教你读报错——这是你从'啥也不会'到'能自己排查问题'最关键的一步。"

为什么要懂这个

新人最大的心理障碍不是"不会写代码"，而是"看到红字就慌"。 一旦你理解了报错的格式和套路，红字就从"恐怖的东西"变成"GPS 导航"—— 它直接告诉你问题在哪、是什么问题、可能怎么修。

UE 程序员 40% 的工作时间在修 bug。会读报错的人修一个 bug 要 5 分钟， 不会读的人同一种错能卡一下午。差距不在智商，在"有没有人教过你怎么读"。

三种报错，三张脸

① 编译错误 —— 语法没写对

什么时候出现：你在 VS 里点"生成"，编译过程中跳出来的红字。

怎么看：打开 VS 的"输出"面板（不是"错误列表"——错误列表会漏信息）。 找到第一条 error，它告诉你：

  • 哪个文件（比如 MyTool.cpp）
  • 第几行（比如 line 47）
  • 错误代码（比如 C2143——语法错误）
  • 一段描述（比如 "missing ';' before '}'"）
🔑 读编译错误的黄金法则

永远只看第一条 error。修完就重新编译。

第一条之后的几百条 error，90% 都是因为第一条炸了引发的连锁反应。 你修完第一条，再编译，可能后面的全没了。一次修 100 条不如一条一条来。

新人最常遇到的几种编译错误：

  • 少分号（C2143）——某行末尾少了个 ;
  • 类型不匹配（C2440）——你把一个字符串赋值给了一个整数变量
  • 找不到标识符（C3861）——你写了一个变量名/函数名，但之前没定义
  • 找不到头文件（C1083）——你 #include 了一个不存在的文件，或 Build.cs 里没加对应依赖

② 链接错误 —— 函数只"声明"了，没"实现"

什么时候出现：编译全都过了，但在链接那一步炸了。标志是 LNK 开头的错误码。

最经典的一条：LNK2019: unresolved external symbol——"有一个名字被提到了， 但我找遍了所有 .obj 文件，没找到它的真身。"

新人遇到 LNK2019 的常见原因：

  • 在 Build.cs 里忘了加某个依赖模块（比如你在代码里调了 Slate 的函数， 但 Build.cs 里没有 "Slate"）
  • 声明了一个函数（在 .h 里写了 void DoSomething();）， 但忘了在 .cpp 里写它的实现（void DoSomething() { ... }）
  • 函数在 .cpp 里实现了，但 .cpp 没有被加入编译（不在任何模块的 Source 目录下）
💡 LNK2019 排查思路

1. 看错误信息里那个 unresolved 的函数名是什么
2. 这个函数属于哪个模块？（去 UE 文档查，或问 AI）
3. 去 Build.cs 的依赖列表里，加上这个模块
4. 重新编译
大多数 LNK2019 都是漏了依赖，不是代码写错了。

③ 运行时错误 —— 编译链接都过了，但程序炸了

这种最难修——因为编译器和链接器都没发现问题， 但程序跑着跑着突然崩溃了。

UE 里的运行时错误通常表现为：

  • 编辑器直接崩溃弹出 Crash Reporter
  • 编辑器没崩，但弹了一个"Assertion Failed"对话框
  • 什么都没弹，但功能不正常（点了按钮没反应、结果显示错了）

Crash Reporter 怎么看？

编辑器崩了之后会弹出一个 Crash Reporter 窗口。里面最重要的信息是 Call Stack（调用堆栈 / 调用栈）——它告诉你崩溃时程序"在干嘛"。

调用栈从下往上看（最上面那一行是崩溃时正在执行的函数）：

UE4Editor-MyTool.dll!UMyClass::DoSomething() Line 47     ← 你的代码
UE4Editor-MyTool.dll!UMyClass::OnButtonClicked() Line 23
UE4Editor-Engine.dll!...                                  ← 引擎内部
UE4Editor-Core.dll!...                                    ← 引擎底层
...
UE4Editor.exe!main()                                       ← 程序入口

你应该先看最上面有没有你的插件/项目名字。 如果有（比如 UE4Editor-MyTool.dll），大概率是你代码里的 bug。 你可以点进去看是哪个文件的哪一行崩的。

如果上面全是引擎代码、没有你的插件，可能是引擎的 bug 或者引擎被你的代码 带进了一个不该进的状态——这时候就截图发给团队里有经验的人帮你一起看。

UE 日志面板 —— 你的"侦探助手"

为什么要懂这个

90% 的运行时问题可以不靠 Crash Reporter，靠日志就能定位。 学会看日志、写日志，是你从"靠别人帮我看"到"自己能排查"的关键一步。

UE 编辑器里有一个"Output Log"面板（Window → Developer Tools → Output Log）。 从你启动编辑器开始，UE 就在一直往这里打印信息——

  • 哪些模块被加载了
  • 哪些资产被读取了
  • 哪些 Warning 被触发了（Warning = 还能跑但不太对）
  • 哪些 Error 发生了（Error = 出问题了但没崩）

你可以在代码里自己往日志里打东西， 用 UE_LOG——Day 0 那个代码示例里就出现过的老朋友：

UE_LOG(LogTemp, Warning, TEXT("现在执行到这里了，变量值是：%d"), MyValue);

这一段干了啥？在日志里打印一行，告诉你"程序跑到这里了，MyValue 的值是 42"。 这就像你在代码里放了一个"监控摄像头"——程序跑到哪里、变量的值是什么， 全记录在日志里。不用靠猜。

💡 "加个 Log 看看"，是 UE 程序员排查问题的第一反应

改代码 → 编译 → 跑 → 看日志里你打的那些行 → 判断问题在哪 → 修 → 再编译。

这个循环是你今后做得最多的操作。UE_LOG 是 C++ 调试的基本手段—— 因为没有"在 UE 编辑器里打断点"那么方便，UE C++ 调试很多时候就是靠日志。

新人遇到报错的标准流程

以后每次看到报错，心里默念这五步：

  1. 别慌，先看第一条——只看第一条 error，读完，理解它说了什么
  2. 定位文件和行号——错误信息里一定有文件名和行号，直接跳过去看
  3. 看错误描述——它说的是类型不匹配？还是找不到函数？还是少符号？
  4. 如果看不懂英文描述——把整条 error 贴给 AI，问"这句话是什么意思，我应该怎么修"
  5. 如果修了还是不行的——截图（包含完整错误信息 + 你的代码那几行），发给 G哥/群里问
报错不是电脑在骂你，
是电脑在用它的语言告诉你问题在哪。
学编程的前半年，其实就是在学"听懂电脑的方言"。
