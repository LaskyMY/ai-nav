桌面应用的系统能力：文件、窗口、托盘和快捷键

网页像住在浏览器里的小房间，桌面应用则直接住进操作系统。它能读写文件、控制窗口、挂到托盘、监听快捷键，也因此更容易踩权限和安全的坑。

📚 课程目录
SCENE · 桌面软件不是网页套壳而已

小K：“我用 Tauri + React 搭了个窗口，那它是不是本质上就是网页？”

G 哥：“界面可以像网页，但桌面应用真正值钱的地方，是它能和操作系统打交道。能不能读文件、开托盘、记窗口位置、绑定快捷键，才是桌面体验的分水岭。”

为什么要懂这个

桌面应用不是“能打开一个窗口”就结束了。用户期待它像本机软件一样工作。

游戏工具、美术辅助工具、截图整理器、批处理小工具，都经常需要访问本地资源。你要知道哪些能力属于前端界面，哪些能力必须交给桌面壳或后端层处理。

第一步：桌面应用比网页多了哪些能力

能力用户感受到什么开发时要注意什么适合问 AI 的方式
文件读写打开本地图片、读取配置、导出文件权限、路径、编码、覆盖风险“这一步应该在前端做，还是通过 Tauri command 做？”
窗口控制记住窗口大小、置顶、最小化到托盘不同系统行为不完全一样“如何保存窗口状态并在下次启动恢复？”
系统托盘关窗口后程序还在后台退出和隐藏要分清楚“托盘菜单需要哪些最小功能？”
全局快捷键不聚焦窗口也能触发操作快捷键冲突、权限、安全风险“这个快捷键是否应该做成可配置？”
系统通知任务完成后弹出提示通知权限、频率、打扰感“哪些事件值得通知，哪些只在界面内提示？”

第二步：前端、桌面壳、系统之间怎么分工

用 Tauri 或 Electron 做桌面应用时，经常会有两层：一层负责界面，一层负责系统能力。新手最容易把“按钮点击”和“文件系统操作”揉成一团。

前端界面

负责按钮、列表、表单、状态展示。它回答“用户看见什么、点哪里”。

桌面壳能力

负责窗口、菜单、托盘、文件对话框、系统通知。它回答“怎么和系统说话”。

业务逻辑

负责整理数据、判断流程、处理错误。它回答“这件事的规则是什么”。

系统资源

文件、目录、剪贴板、网络、权限。它回答“真实资源在哪里，是否允许访问”。

一句话记住

按钮在前端，能力在系统层。前端发起请求，桌面壳去碰文件、窗口、托盘和系统 API，最后把结果安全地交回界面。

第三步：最小桌面体验清单

做一个能展示的桌面工具，至少要想清楚这些基础体验，否则它会像“网页临时包了一层壳”。

  • 窗口关闭时，是退出程序，还是隐藏到托盘？
  • 用户上次的窗口大小和位置，要不要记住？
  • 文件保存失败时，错误提示放在哪里？
  • 用户选择的路径，下次启动要不要记住？
  • 快捷键是否可配置？冲突时怎么提示？
  • 后台任务完成后，是系统通知还是界面内提示？

第四步：不要让 AI 一口气接系统权限

AI 互动现场：先做假能力，再接真系统
你

给我的工具加一个“选择文件夹并批量处理图片”的功能。

AI

我可以直接接文件系统、遍历目录、写入结果……

你

先不要碰真实文件。请先做一个假数据原型：模拟选择 5 个文件，展示处理进度和错误状态。等界面流程确认后，再接真实文件 API。

AI

明白。先验证交互闭环，再接系统能力，可以降低误删和权限风险。

我想给桌面应用添加一个系统能力：[文件选择 / 托盘 / 快捷键 / 通知 / 窗口状态]。 请先不要直接实现。 请你先输出： 1. 这个能力涉及前端、桌面壳、系统权限中的哪几层； 2. 最小原型怎么用假数据验证； 3. 真接系统 API 时有哪些风险； 4. 需要哪些用户提示和错误处理； 5. 建议分几步实现，每一步怎么验证。
桌面应用的质感，来自它尊重操作系统。
能接系统能力不难，难的是接得克制、可控、可解释。
