引擎、插件、扩展

小K 终于搞清楚了他岗位描述里的"工具开发"——不是改引擎，不是写游戏逻辑， 是给编辑器加"功能按钮"。但要理解这个，得先搞清楚"引擎"和"插件"到底是什么关系。

SCENE 4 · 第四天下午

小K： "G哥，咱们办公室有人说'我在改引擎'，有人说'我在写插件'，有人说'我在做工具'—— 这三个是一回事吗？"

G 哥（放下咖啡）： "好问题。引擎是底座，插件是积木，工具是你用积木拼出来的东西。 你今天把这层关系捋清楚了，岗位描述里每个词就都有落脚点了。"

为什么要懂这个

"引擎""插件""模块""工具"——这四个词在 UE 开发中天天出现， 但很多干了一年的人都说不清它们的确切关系和边界。 搞清楚了，你就知道"我能动什么"和"我该在哪写代码"。

游戏引擎到底是什么？

把"引擎"两个字从技术上扒开，它就是一个巨大的代码库。 它在游戏（或编辑器）启动时被加载，然后提供几个核心能力：

  • 渲染——把 3D 场景画到屏幕上
  • 物理——碰撞检测、重力、布料
  • 音频——播放声音、空间音效
  • 输入——键盘、鼠标、手柄
  • 网络——多人联机
  • 编辑器框架——你看到的那个 UE 编辑器界面本身

这些东西不是 UE 发明的——每个游戏引擎都有。 UE 特别的地方是，它把这些能力包装得很"好用"， 并且提供了一个完整的编辑器让你在可视化界面里操作它们。

🔑 一句话定义

游戏引擎 = 渲染 + 物理 + 音频 + 输入 + 网络 + 编辑器框架 + …… 的一个巨大 C++ 代码库。

UE 引擎源码大约有几万个 .cpp 文件。你装源码版 UE 的时候，就是把这堆文件 拉到本地、编译一遍。

引擎和项目：到底谁"包含"谁？

为什么要懂这个

很多人以为"项目包含引擎"——其实反过来。引擎是个大容器，项目是引擎加载的一套配置和资产。

一个常见误解："我打开 UE 项目，所以项目里有引擎。"

实际上：引擎是主程序，项目是引擎加载的"一套设定"。

UE 编辑器（UnrealEditor.exe）启动的时候，会加载你指定的 .uproject 文件， 然后根据这个文件里的信息去找——" 这个项目有哪些模块？ 有哪些插件？ 资产放在哪个 Content 文件夹？ 配置是什么？"

所以你的 .uproject 文件（昨天在 Project 文件夹看到过）就是一张"说明书"， 告诉引擎："加载这些这些这些。"

Plugin — 往引擎这个"操作系统"里装软件

为什么要懂这个

你作为一个"工具开发者"，你的工作不是改引擎，而是写 Plugin。 理解 Plugin 的机制，就是你理解自己工作的第一步。

把 UE 引擎想象成 Windows 操作系统。Windows 本身提供了文件管理、网络、 显示这些基础能力。但你要写文档，你得装一个 Word——Word 就是一个"插件"。

UE 的 Plugin 就是这个概念：往引擎上加一块独立的功能积木。 引擎提供基础能力（渲染、输入、编辑器框架）， Plugin 调用这些能力来实现具体功能（比如"批量重命名资产"、" 检查贴图参数是否规范"）。

Plugin 的好处是独立：你写的插件不会影响别人的插件， 可以单独启用/禁用，可以单独提交到版本控制。

Editor Plugin vs Runtime Plugin —— 工具开发的关键分界线

为什么要懂这个

你的岗位是"工具开发"——你写的基本上全是 Editor Plugin。 如果这个分不清，你可能会把 Editor 代码写成 Runtime 代码， 导致打包出来的游戏带着不该带的代码。

Editor Plugin（编辑器插件） 只在 UE 编辑器运行时生效。游戏打包时不会带进去。

举例：批量重命名资产、检查贴图规范、一键生成目录结构、可视化调试面板。

Runtime Plugin（运行时插件） 编辑器和打包后的游戏里都生效。

举例：一个自定义的物理系统、一个新材质类型、一个网络同步方案。

← 这是 gameplay 程序员写的

你的插件在 .uplugin 文件里会声明自己的类型：

  • "Type": "Editor" → 只在编辑器里跑
  • "Type": "Runtime" → 编辑器+游戏都跑
  • "Type": "EditorOnly" → 引擎启动时就有，游戏里没有

大多数工具插件写 "Type": "Editor" 就够了。

UCLASS / UFUNCTION / UPROPERTY —— C++ 和 UE 编辑器之间的"翻译官"

为什么要懂这个

这三个宏是你今后每天都要写的东西。不理解它们的存在意义， 你就会觉得是在"背咒语"而非"用工具"。

它们是 C++ 代码"暴露"给 UE 编辑器的桥梁。 你在 C++ 里写了一个类、一个函数、一个变量——但编辑器默认看不到它。 你得用这三个宏告诉引擎"嘿，这个可以给编辑器/蓝图用"。

用最朴素的话解释这三个：

  • UCLASS()：声明"这是一个 UE 认识的类"。 不加这个，编辑器根本不知道你的类存在。
  • UFUNCTION()：声明"这个函数可以给蓝图/编辑器调用"。 不加这个，蓝图里搜不到你的函数。
  • UPROPERTY()：声明"这个变量可以在编辑器面板里看到和修改"。 不加这个，你的变量在细节面板里不显示。

用一段代码感受一下：

// 一个没有 UE 标记的普通 C++ 类
class NormalClass
{
    int32 Value;              // 编辑器看不见
    void DoSomething();       // 蓝图调不了
};

// 加了 UE 标记的类
UCLASS()
class UMyToolClass : public UObject
{
    GENERATED_BODY()

public:
    UPROPERTY(EditAnywhere)   // ← "这个变量在编辑器面板里可以改"
    int32 Value;

    UFUNCTION(BlueprintCallable)  // ← "蓝图可以调用这个函数"
    void DoSomething();
};

第一段代码对 UE 编辑器来说等于不存在。 第二段代码能让编辑器看到 Value 变量，让蓝图能调用 DoSomething 函数。

这就是三个宏做的事情：让"C++ 的世界"和"UE 编辑器的世界"能说话。 不加它们，你写再多 C++ 代码，编辑器和蓝图都当你是空气。

🔑 记住这个画面

C++ 和 UE 编辑器是两个世界。中间隔了一道玻璃墙。
UCLASS 在墙上开个门，让类能进出。
UFUNCTION 在门上装了个对讲机，让蓝图能"喊"这个函数。
UPROPERTY 在墙上挂了个显示屏，让编辑器能看到和改这个变量。

这就是所谓的"反射系统"——UE 引擎能"看到"你的 C++ 代码， 全靠这三个宏和背后的代码生成工具（UHT，Unreal Header Tool）。

引擎 vs 插件 vs 工具：三者的关系一句话

  • 引擎：楼。提供水电煤（渲染、物理、音频、编辑器框架）。
  • 插件：房间。在楼里占一块空间，有自己的水电接口。
  • 工具：房间里的家具和电器。你每天做的具体功能。

你作为工具开发者，做的事是：在 Plugins 里开一间房（Editor Plugin）， 往里面摆各种家具（用 UFUNCTION 暴露给编辑器调用的功能）， 让美术/策划/其他程序能通过编辑器界面使用这些家具。

引擎是底座，插件是积木，
UCLASS / UFUNCTION / UPROPERTY 是积木之间的接口。
