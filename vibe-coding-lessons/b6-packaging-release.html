打包发布：图标、安装包、签名和自动更新

项目在自己电脑上能跑，只是开发完成的第一步。真正交给别人用时，还要面对图标、安装包、系统安全提示、版本号、更新和卸载。

📚 课程目录
SCENE · 能跑不等于能发

小K：“我把项目文件夹压缩发给同事，让他自己 npm install 然后 npm run tauri dev，可以吗？”

G 哥：“那叫发源码，不叫发布软件。用户期待的是双击安装、打开就用、坏了能更新。”

为什么要懂这个

桌面应用的最后 20%，经常是最容易被新手低估的 80% 麻烦。

打包发布不是简单点一个 build。你要让系统信任它，让用户知道版本，让别人能安装、能卸载、能更新，还要在不同机器上验证它不是只在你电脑能跑。

第一步：发布桌面软件到底要交付什么

交付物用户看到什么开发者要准备什么常见坑
应用图标桌面、任务栏、安装器里的图标多尺寸图标、透明背景、平台格式只准备一张 PNG，打包后糊掉或缺失
安装包.exe、.msi、.dmg、.app、.deb 等构建配置、安装路径、卸载逻辑自己机器能打开，别人机器缺依赖
版本号v1.0.0、v1.0.1语义化版本、更新说明改了很多但版本号不变，用户不知道装的是哪版
签名系统更少弹安全警告代码签名证书、发布流程未签名软件被拦截或显示未知发布者
更新机制提示有新版本、下载更新更新服务器、版本清单、回滚策略第一版就做自动更新，复杂度爆炸

第二步：先分清内部演示版和正式发布版

不是所有软件第一天都要签名、自动更新、官网下载安装。你可以先做内部演示版，再做小范围试用版，最后才做正式发布。

演示版

能在自己电脑和同事电脑打开，主要验证功能和流程。

试用版

有基本图标、版本号、打包说明、已知问题列表。

正式版

考虑签名、安装器、更新、崩溃日志和回滚策略。

一句话记住

发布不是把代码发出去，而是把使用风险降下来。用户不应该懂 npm、Rust、依赖和构建命令，用户只应该知道怎么安装、怎么打开、怎么更新。

第三步：发布前检查清单

干净机器测试

找一台没装开发环境的机器测试安装和启动。

首次启动体验

默认配置、空状态、权限提示是否清楚。

升级测试

从旧版本安装到新版本，数据是否还在。

卸载测试

卸载后哪些数据保留，哪些缓存清理。

第四步：让 AI 帮你做发布计划，而不是直接 build

AI 互动现场：把“打包一下”变成发布流程
你

帮我把这个桌面应用打包。

AI

可以，运行 build 命令即可……

你

先不要打包。请先根据当前项目识别打包工具、目标平台、图标配置、版本号位置和产物目录，然后给我一份发布前检查清单。

AI

明白。我会先查配置，再给可验证的发布步骤。

第五步：自动更新要晚一点再做

自动更新听起来很高级，但它会引入签名、服务器、版本清单、下载失败、更新失败回滚等问题。新手项目可以先用“手动下载新版本 + 更新说明”的方式，等用户真的需要频繁更新，再考虑自动更新。

先做手动发布

产物清楚、版本号清楚、更新说明清楚、用户知道去哪下载。

以后再做自动更新

稳定后再加更新通道、签名验证、回滚机制和灰度策略。

请帮我为桌面应用制定发布计划。 项目技术栈：[Tauri / Electron / Flutter / 其他] 目标平台：[Windows / macOS / Linux] 发布阶段：[内部演示 / 小范围试用 / 正式发布] 请输出： 1. 当前需要准备哪些发布材料； 2. 图标、版本号、应用名分别在哪里配置； 3. 打包产物会在哪里生成； 4. 发布前必须验证哪些场景； 5. 哪些高级能力现在先不要做，比如自动更新、签名、云同步。
能跑，是开发者视角。
能安装、能升级、能卸载、能被信任，才是用户视角的完成。
