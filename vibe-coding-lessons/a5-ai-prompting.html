跟 AI 好好说话

小K 试着自己写代码——写不出来。G哥说你试试问 AI。 结果问出来的代码要么跑不起来、要么完全不对。不是 AI 没用，是小K 还不会"问"。

📚 课程目录
SCENE 6 · 第六天下午

小K（把脸埋在手里）： "G哥，我在网上抄了一段代码放到项目里，编译都不通过。然后我去问 AI， 它给我写了 200 行，更跑不起来——我是不是不适合写代码？"

G 哥（把椅子拉过来）： "不是你不行，是你还不会'使唤'AI。你把 AI 当搜索引擎用——问一句，要一个答案。 但 AI 的用法是：它像一个很聪明但完全不了解你项目上下文的新同事。 你得先给他讲清楚背景，他才能给你有用的东西。"

G 哥（敲了几下键盘）： "来，我给你看同样一个需求，'不会问的人'和'会问的人'问出来的差别有多大。"

为什么要懂这个

Vibe Coding 时代，写代码的能力正在从"记忆语法"变成"准确描述需求"。 你今后写代码的流程大概率是：想清楚要什么 → 描述给 AI → 读 AI 的输出 → 改到能跑。 这个流程里最值钱的能力不是背语法，是把模糊需求翻译成清晰指令。

作为一个刚入行的工具开发者，你不会独立从零写一个复杂功能。 但你如果能准确地告诉 AI "我在做什么项目、用的是 UE5.4、要加一个 Editor Plugin、 这个 Plugin 要提供一个右键菜单按钮、点了之后弹一个窗口"—— 你就已经比 80% 的新人强了。

先看两组对话——差距在哪，一眼就懂

❌ 不会问的人

小K 的第一版提问

"给我写一个 UE 工具，能批量改资产的名字。"

AI 回了一堆——但写的是 Runtime Actor 的代码， 用的是 C++ 标准库的文件操作，完全不知道 UE 有 AssetTools。—— 根本用不了。

✅ 会问的人

G哥 的提问版本

"我在做一个 UE5.4 的 Editor Plugin（不是 Runtime）。想加一个功能： 在 Content Browser 里选中多个资产（贴图/材质），右键菜单出现一个按钮 '批量改名'，点了之后弹出一个 Editor Utility Widget 窗口， 窗口里可以输入前缀和后缀，点确认后批量重命名选中的资产。

请用 C++ 写，告诉我需要建哪些文件、每个文件放哪个目录、 以及 Build.cs 里要加什么依赖。"

AI 回的代码直接就能放进项目里，改几行就能跑。——差的是一个"上下文"。

这两段提问的差距在哪？

  • 第一个只说了"要什么结果"——"批量改名"。
  • 第二个说了"在什么环境、给谁用、触发方式、交互流程、技术要求"。

AI 就像一个能力极强但完全不了解你项目的新同事。 你给他越多的上下文，他给你的东西越能直接用。 你什么都不说，他就靠猜——猜错就是你的成本。

Vibe Coding 的四个核心原则

为什么要懂这个

这四个原则不是"技巧"，是你跟 AI 协作的底层逻辑。 掌握了它们，你今后跟任何 AI 工具（Claude、ChatGPT、Copilot）协作的效率都会翻几倍。

原则一：先给环境，再提需求

在说"我要什么"之前，先说"我在哪"：

  • 引擎版本：UE5.4 还是 5.3？
  • 项目类型：源码版还是启动器版？
  • 插件类型：Editor Plugin 还是 Runtime Plugin？
  • 已有基础设施：你项目里已经有某个框架了吗？

比如："我用的 UE5.4 源码版，在做一个 Editor Plugin， 插件名叫 MyTool，已经有一个 Editor Utility Widget 的基础框架。"

原则二：说清楚"触发方式"和"交互流程"

不要只说"做一个功能"，要说清楚——

  • 用户从哪触发？（Content Browser 右键？编辑器工具栏按钮？独立窗口？）
  • 触发之后发生什么？（弹窗？直接执行？多步向导？）
  • 输入是什么？输出是什么？

原则三：把大需求拆成小块，一次只问一个

❌ "给我做一个完整的资产管理系统"
✅ "先帮我写一个函数，输入一个资产路径，返回这个资产的所有引用者列表"

AI 在处理"大而全"的需求时容易遗漏和幻觉。 你拆成小块，每一步验证过了再问下一步，效率反而更高。

原则四：让 AI 告诉你"他还需要什么信息"

在你的提问最后加一句： "如果你还需要更多信息才能给出准确的代码，请先问我。"

这句话会让 AI 在"猜"之前先反问你——避免它基于错误假设写一堆废代码。

AI 给你的代码，你该怎么看？

为什么要懂这个

AI 写的代码不是"拿来就能用"——它可能有小错误、可能不符合你项目的规范、 可能用了过时的 API。你得学会"读 AI 的输出"——而读代码的能力， 正是你前面 5 天在慢慢建立的东西。

拿到 AI 给的代码后，你的标准流程应该是：

  1. 读一遍——不要求全懂，但至少要认出"哦，这里在定义一个类， 这里在调一个函数，这里在处理错误"。Day 0 的"四个基本元素"就是干这个的。
  2. 检查依赖——AI 用了哪些 UE 模块？你的 Build.cs 里有没有这些模块？ 如果没有，加上。忘了加依赖是编译失败的第一大原因。
  3. 放到对的目录——.h 放 Public/，.cpp 放 Private/。放错了 UBT 找不到。
  4. 编译——如果能编译过，你已经跑通了 80% 的路。
  5. 跑一遍试试——启动编辑器，触发你的工具，看行为对不对。
  6. 把报错贴回给 AI——如果编译报错或运行不对，把完整的错误信息贴回给 AI， 加上"我刚才让你写的代码编译报了下面这个错，请帮我修正"。
🔑 Vibe Coding 的核心循环

描述需求 → AI 给代码 → 你读+编译 → 如果报错，贴回给 AI → AI 修正 → 再编译 → 跑通了，你再去理解它到底干了什么。

这个循环跑几遍，你不仅得到了能用的代码，还顺便学会了写代码。 因为你在读、在改、在调试——这些正好就是学编程最高效的方式。

给你的"万能提问模板"

保存下面这个模板。前半年每次问 AI，就照着填：

【环境】
- UE 版本：
- 项目类型：源码版 / 启动器版
- 插件类型：Editor Plugin / Runtime Plugin
- 插件名：
- 使用的 IDE：Visual Studio 2022

【需求】
- 我要实现什么功能：
- 用户从哪里触发：
- 触发后发生什么：

【约束】
- 只需要 C++ 代码 / 需要蓝图配合
- 如果有代码规范要求，写在这里
- 如果有特殊限制（不能用某模块等），写在这里

【输出要求】
- 请列出需要新建/修改的所有文件，以及每个文件的完整路径
- 请在代码的关键位置加上注释
- 如果你需要更多信息，请先问我
不会写代码不是问题。
不会描述你要什么，才是问题。
