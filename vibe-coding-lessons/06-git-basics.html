Git 是什么：给代码做存档和回滚

小K 终于敢让 AI 改代码了，但新的恐惧来了：万一 AI 一口气把项目改坏，我怎么回到之前那个能跑的版本？

📚 课程目录
SCENE · 第一次想回到过去

小K：“G哥，我让 AI 美化页面，它改了 8 个文件。现在页面能打开，但按钮全歪了。我想回到刚才那个版本，怎么办？”

G 哥：“这就是 Git 要解决的问题。Git 不是高级程序员才用的东西，它是你和 AI 协作时的安全绳。”

为什么要懂这个

VibeCoding 最大的风险不是写得慢，而是 AI 改得太快。没有版本管理，你就不敢大胆试。

Git 可以把项目在某个时间点的状态保存下来。你可以比较“改前”和“改后”，可以给每次有效改动打一个存档点，也可以在方向错了的时候回到上一个能跑的版本。

第一步：Git 不是 GitHub

新手最容易把 Git 和 GitHub 混成一件事。它们经常一起出现，但不是同一个东西。

名字它是什么人话理解常见误会
Git版本控制工具在你电脑上给代码做存档、对比、回滚。以为不用 GitHub 就不能用 Git。其实 Git 本地就能用。
GitHub / GitLab远程代码平台把代码仓库放到网上，方便备份、协作、审核。以为它们就是 Git 本身。
Repository / Repo仓库一个被 Git 管起来的项目文件夹。以为 repo 是某个神秘服务器，其实本地项目也可以是 repo。
Commit一次提交一个明确的存档点，记录“这次改了什么”。把 commit 当成保存按钮乱按，不写说明。

第二步：Git 的三层空间

Git 最难的地方不是命令，而是它有几个“空间”。你不用一开始全背，但要知道文件正在经历哪一步。

Working Tree

工作区。你正在编辑的真实文件，都在这里。

Staging Area

暂存区。你挑选“这次准备提交哪些改动”的地方。

Commit History

提交历史。一个个存档点串成时间线。

Remote

远程仓库。团队共享和备份的位置，例如 GitHub、GitLab。

一句话记住

编辑文件不等于提交，提交不等于上传。先改文件，再选择要提交的改动，再生成 commit；如果有远程仓库，最后才 push。

第三步：最常见的 Git 黑话

黑话它在说什么你要关心什么
diff改动对比AI 改了哪些行、删了哪些行、有没有碰不该碰的文件。
branch分支单独开一条修改路线，不影响主线。
merge合并把一条分支的改动合回另一条。
conflict冲突两边改了同一块内容，Git 不知道该保留谁。
checkout / switch切换切到另一个分支或历史状态。
revert反向撤销生成一个新提交，把某次提交的效果抵消掉，比较适合协作场景。

第四步：和 AI 协作时，Git 应该怎么用

最专业的 VibeCoding 不是“让 AI 一次做完”，而是把项目切成很多个可控的小存档点。

01

开始前确认当前项目能运行，保存一个干净的 commit。

02

让 AI 一次只改一个目标，例如“只改课程首页卡片，不碰脚本”。

03

改完先看 diff，确认它改了哪些文件。

04

跑一遍最小验证，能打开、链接没断、主要功能还在。

05

验证通过再 commit，提交信息写清楚这次完成了什么。

AI 互动现场：先看 diff，再夸 AI
你

你已经改完了吗？

AI

改好了，页面应该更漂亮了。

你

先别总结。请列出这次修改过的文件、每个文件的改动目的、是否包含无关改动，并给我一份验证清单。

AI

好的，我会先按文件列 diff 摘要，再说明验证方式。

第五步：Git 和 P4、SVN、备份文件夹有什么关系

游戏公司里经常能见到 Perforce（P4），因为它很适合管理大量二进制资源、大文件和美术资产。Git 更适合代码和文本文件。你不用在第一天就成为版本控制专家，但要知道它们解决的是同一类问题：保存历史、协作修改、出现问题时能回退。

Git 更像代码时间线

适合小步提交、分支开发、看 diff、多人代码协作。

P4 更像大型资产仓库

适合游戏项目里的二进制资产、锁文件、集中式流程。

请你作为我的版本管理教练，帮我检查这次 AI 修改是否适合提交。 要求： 1. 先列出修改过的文件； 2. 按“功能改动 / 样式改动 / 配置改动 / 可疑改动”分类； 3. 指出有没有不该动的文件； 4. 给出建议提交信息； 5. 如果不建议提交，请告诉我应该先验证什么。
Git 的本质不是命令。
它是在告诉你：大胆试，但每一步都要能回来。
