走进 UE 项目

小K 终于要真正打开一个 UE 项目了。.uproject 文件是什么？Module 是什么？ Build.cs 是什么？C++ 代码在 UE 里是怎么被"找到"并编译的？

SCENE 5 · 第五天早上

小K： "G哥，我打开项目文件夹，看到 .uproject 右键能'生成 VS 项目文件'—— 然后 VS 里出现了几千个文件。这些文件是怎么'出现'的？ 为什么我写的 .cpp 能被 UE 找到？"

G 哥： "你问到了 UE 最核心的一个机制——UBT。今天把 .uproject → Module → Build.cs → UBT → 编译这条链路走一遍。走完之后，你看任何 UE C++ 项目的目录， 脑子里都会自动浮现一张'编译管线图'。"

为什么要懂这个

这一天的内容是你今后每天改代码时，背后的"游戏规则"。 如果你不理解 .uproject / Module / Build.cs 的关系， 你加一个新文件、改一个依赖、甚至只是给插件改个名字，都会莫名其妙地编译失败。

而且——这些知识网上几乎没有"给人话"写的版本。你今天花 30 分钟看懂这套规则， 后面永远不用再被"为什么找不到我的文件"困住。

.uproject —— 项目的"身份证"

打开一个 .uproject 文件（用记事本就行），你会看到类似这样的内容：

{
    "FileVersion": 3,
    "EngineAssociation": "5.4",
    "Category": "Games",
    "Description": "我的 UE 项目",
    "Modules": [
        {
            "Name": "MyProject",
            "Type": "Runtime",
            "LoadingPhase": "Default"
        }
    ],
    "Plugins": [
        {
            "Name": "MyTool",
            "Enabled": true
        }
    ]
}

这是一个 JSON 文件——一种人类和机器都能读的数据格式。 里面最重要的几项：

  • "EngineAssociation"：告诉 UE"我绑定哪个版本的引擎"
  • "Modules"：列出这个项目自己的 C++ 模块
  • "Plugins"：列出这个项目启用了哪些插件

UE 编辑器启动时读这个文件，就知道"该加载哪些东西"。 你右键 .uproject → "Generate Visual Studio project files" 的时候， UE 也读这个文件，然后去找到所有相关的 .cpp / .h， 生成一个 VS 能打开的 .sln 解决方案。

Module —— 代码的"集装箱"

为什么要懂这个

Module 是 UE 组织 C++ 代码的基本单位。你的每一个插件至少包含一个 Module。 搞清楚"模块"的概念，你才知道为什么有时候加了 .cpp 却编译不到—— 因为它没有被任何模块包含。

UE 项目的 C++ 代码不是散装的——它们被组织成一个个 Module（模块）。 一个 Module 就是一个"代码集装箱"：一套相关的 .cpp / .h 打包在一起， 有共同的编译规则，有明确的依赖关系。

UE 引擎本身就由几百个 Module 组成。比如：

  • Core——最底层的基础设施（字符串、容器、数学库）
  • CoreUObject——UObject 系统（UCLASS 那套机制的实现）
  • Engine——引擎核心功能（Actor、Component、Level）
  • UnrealEd——编辑器框架（你写 Editor Plugin 时最重要的依赖）
  • Slate——UI 框架

你的插件也至少有一个 Module（在 Plugins/MyTool/Source/ 下）。 如果你想让某些代码只在编辑器里跑、另一些在游戏里也跑， 你可以把插件分成两个 Module——一个 Editor、一个 Runtime。

Build.cs —— 模块的"说明书"

每个 Module 文件夹下都有一个 xxx.Build.cs 文件。 这是一个 C# 文件（不是 C++），它是给你的模块写"说明书"的地方：

// MyTool.Build.cs
using UnrealBuildTool;

public class MyTool : ModuleRules
{
    public MyTool(ReadOnlyTargetRules Target) : base(Target)
    {
        PCHUsage = PCHUsageMode.UseExplicitOrSharedPCHs;

        // 这个模块依赖哪些其他模块
        PublicDependencyModuleNames.AddRange(new string[] {
            "Core",
            "CoreUObject",
            "Engine",
            "UnrealEd",       // ← 编辑器模块，写 Editor Plugin 必备
            "Slate",
            "SlateCore"
        });

        // 只在编辑器环境需要的依赖
        if (Target.bBuildEditor)
        {
            PrivateDependencyModuleNames.Add("EditorStyle");
        }
    }
}

这个文件告诉了 UBT 几件关键的事：

  • 依赖列表：这个模块要调用哪些其他模块的功能。 比如你调了 Slate UI 的函数，就必须在这里写上 "Slate"。
  • 编译选项：预编译头怎么处理、是否有第三方库等。
⚠️ 新人最容易漏的一步

你在代码里写了 #include "SlateCore.h"， 但忘了在 Build.cs 的依赖列表里加 "SlateCore"。 编译器会告诉你：找不到这个头文件。

规则：你在 .cpp 里 #include 了谁， 就要在 Build.cs 的依赖里加上对应的模块名。 两者必须同步。漏一个就编译不过。

UBT —— 编译背后真正的大管家

为什么要懂这个

你在 VS 里点"生成"，背后不是 VS 在编译——是 UBT。 理解了 UBT 的角色，你才能理解为什么 UE 编译跟普通 C++ 项目编译行为不一样。

UBT = Unreal Build Tool。它是 UE 自己的编译管理程序。

普通 C++ 项目：你写 .cpp → VS 调 MSVC 编译 → 链接 → 出 .exe。

UE C++ 项目：你写 .cpp → UBT 先扫描所有 .uproject / .uplugin / Build.cs → 生成一个"编译计划"（哪些文件属于哪些模块、依赖关系是怎样的）→ 然后调 MSVC 按计划编译 → 链接 → 出 .dll / .exe。

UBT 多出来的这一步"扫描+计划"非常关键，因为：

  • 它自动发现你的 .cpp 文件——你不需要手动加到什么列表里。 只要 .cpp 放在正确的 Source 目录下，UBT 就会找到它。
  • 它解析依赖——读 Build.cs 搞清楚"谁依赖谁"， 然后决定编译顺序。
  • 它做增量判断——知道哪些文件你改过了，只编译那些。

一条完整的"代码被发现"链路

现在我们把整条链路串起来。你新建了一个 .cpp，里面写了一些代码——UE 是怎么"发现"它的？

  1. 你把 my_tool.cpp 放在 Plugins/MyTool/Source/MyTool/Private/ 下
  2. UBT 扫描 .uproject 时发现了 MyTool 插件
  3. UBT 接着读 MyTool.uplugin，发现它有一个 Module 叫 MyTool
  4. UBT 去 Source/MyTool/ 下找，读 MyTool.Build.cs，知道了依赖关系
  5. UBT 自动把 Private/ 和 Public/ 下的所有 .cpp 纳入编译列表
  6. UBT 把编译列表交给 MSVC，MSVC 开始干活
  7. 编译完后，生成 MyTool.dll，放在 Binaries/ 下
  8. UE 编辑器启动时加载 MyTool.dll，你的代码"活了"
💡 这就是 UE 比普通 C++ 项目"智能"的地方

你不需要手动把 .cpp 加到什么"项目文件列表"里。 UBT 会自动扫描 Source 目录下的所有 .cpp。 你只要把文件放在对的文件夹里，UBT 就会找到它。

这就是"Convention over Configuration"（约定大于配置）——UE 用"文件放在哪" 来决定"它属于哪个模块"，而不是让你在一堆配置菜单里选。

.uproject 告诉引擎"有哪些模块"，
Build.cs 告诉 UBT "这个模块依赖谁"，
UBT 自动扫 Source 目录下的所有 .cpp，
然后交给 MSVC 一个个翻译。
