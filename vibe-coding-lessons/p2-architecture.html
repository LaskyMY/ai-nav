技术选型：让 AI 先给权衡，再做决定

真正有条理的 AI 开发，不是让模型直接开写，而是先要求它列方案、讲取舍、给推荐、说明不选什么。

📚 课程目录
SCENE · 不急着搭项目

小K：“需求有了，是不是可以让 AI 直接生成项目？”

G 哥：“先别。你要让 AI 把技术路线讲明白。选型不是炫技，是给后面的所有实现减少分叉。”

为什么这一节很关键

技术选型的核心不是“选最强”，而是选一个最适合当前目标的约束系统。

这次目标是做一个能展示 Vibe Coding 流程的桌面待办工具。所以我们不追求大而全，而是追求：能快速起原型、能用 Web 技术美化、能打包成桌面应用、能被 Codex 稳定修改和验证。

第一步：让 AI 给出候选方案和评估维度

基于这份项目简报，请你不要直接写代码，先做技术选型。 目标：桌面悬浮待办工具，强调 UI 质感、快速原型、离线本地保存、后续可打包发布。 请比较至少 4 种方案： - Tauri + React + TypeScript - Electron + React - 纯 Web / PWA - Flutter Desktop 请按这些维度打分：开发速度、包体积、UI 灵活性、系统能力、学习成本、AI 辅助友好度、后续维护成本。 最后给出推荐方案，并说明哪些方案不适合当前项目。
AI 互动现场：不要只听“最佳方案”
你

基于这个待办工具，请给我技术选型建议。

AI

推荐 Electron + React + SQLite，扩展性最好，也方便以后做系统托盘、通知和本地数据库。

你

你现在像在给正式产品做架构。请反过来批判这个方案：对零基础课程、两天原型、演示稳定性来说，它哪里过重？

AI

确实过重。SQLite、托盘和通知会增加环境复杂度。课程阶段更适合 React + Vite + localStorage，先证明交互闭环，再讨论桌面壳。

有意思的转折

这里最“高级”的不是 AI 给了答案，而是你要求 AI 反驳自己的答案。这样选型就从“听 AI 拍脑袋”变成了“让 AI 给论据，人做决策”。

第二步：把 AI 的建议变成选型矩阵

方案优势劣势结论
Tauri + React包体小，能调用系统能力，前端生态成熟，AI 很擅长改 React/CSS。Rust 和窗口 API 有学习成本。主方案。适合做“像产品”的桌面工具。
Electron + React成熟、资料多、桌面能力强。包体和资源占用偏大，展示“轻量悬浮工具”时说服力弱。备选，但不是这次最优。
纯 Web / PWA最快，部署简单，验证 UI 方便。缺少真实桌面悬浮、托盘、窗口控制能力。可做原型，不适合作为最终形态。
Flutter Desktop跨平台 UI 一致，性能好。生态和 AI 生成前端 UI 的效率不如 React/CSS。不选，偏离本次 Vibe Coding 目标。

第三步：定义“最小可行技术路线”

选型不是终点。真正让开发顺起来的是把技术路线拆成阶段：先证明产品能跑，再证明体验好，再证明质量可控。

阶段 1

用 React 先做 Web 原型：验证信息结构、状态流转和 UI 形态，不急着碰系统托盘。

阶段 2

接入 Tauri：把 Web 原型装进桌面壳，补窗口尺寸、悬浮和托盘能力。

阶段 3

用 UI UX Pro 做视觉审查：检查层级、触控目标、色彩对比、阅读密度和动效节奏。

阶段 4

用 Codex 做工程化收尾：拆组件、补测试、跑冒烟、修边界问题。

第四步：让 AI 解释“不做什么”

一个项目看起来专业，不是因为做得多，而是因为知道哪些暂时不做。

  • 不做账号系统：学习项目不需要后端复杂度。
  • 不做多端同步：同步冲突会吞掉大量时间。
  • 不做自定义插件：会让 MVP 范围失控。
  • 不一开始追求完美动画：先让核心流程闭环。
这一节最“牛”的地方，是你让 AI 先当架构评审。
不是“AI 说用什么我就用什么”，而是AI 给论据，人做决策。
