概念链总览——从底层到顶层

总览

AI 世界不是凭空出现的。每个新概念都是在之前概念的局限上生长出来的：

LLM 能预测下一个词，但记不住太长的对话 → 有了 Context Window

模型没有目标，不知道怎么"对话" → 有了 Prompt

只会生成文字，不会查天气、不会算数 → 引入了 Tool / Function Calling

每个 API 的工具格式不一样，太乱了 → 有了 MCP 统一协议

单个工具不够，需要自主规划+循环执行 → 这就是 Agent

Agent 能力复用和组合 → 形成 Agent Skill

🧠

LLM——预测下一个词的机器

第 1 章

大语言模型 (LLM) 的核心任务极其简单：给定前面的文字，猜下一个最合适的词。

比如输入 "中国的首都是"，模型会输出 "北京"。输入 "1+1="，模型会输出 "2"。 把"猜下一个词"这个能力训练到极致（大量数据+大算力+注意力机制），就产生了涌现—— 模型开始表现出推理、翻译、写代码等"智能"行为。

LLM 内部是一个巨大的神经网络（注意力机制 + 前馈网络 × N层），通过海量文本训练学会了语言的统计规律。 但它没有"意识"，没有"目标"，也没有"记忆"——它只是一台精密的、会接话的机器。

💡 关键洞察：LLM 本身只是一个"文本接龙器"。让它变聪明、变有用的，是围绕它构建的所有上层机制——从 Prompt 到 Agent。
✂️

Token——AI的"最小语义单元"

第 2 章

LLM 不直接看"字"，而是看 Token（词元）。一个 Token 可能是：一个完整的常见词、词的一部分（子词）、一个标点符号、或一个特殊标记。

英文 Token 化

"unbelievable" → "un" + "believe" + "able" (3 tokens)
"Hello world!" → "Hello" + " world" + "!" (3 tokens)

中文 Token 化

"人工智能" → "人工" + "智能" (2 tokens)
"我喜欢编程" → "我" + "喜欢" + "编程" (3 tokens)

为什么 Token 重要？
1. 计费单位：API 按 Token 数量收费（输入+输出）
2. 上下文窗口的"容量"：模型的 Context Window 用 Token 数来衡量
3. Token 不是字：1000 个中文字 ≈ 1500-2000 个 Token（取决于分词器）
🪟

Context — AI的"记忆"，但有上限

第 3 章

Context（上下文）= 模型当前能"看到"的所有内容的集合。

每次你向模型发送消息，实际发送的不是"你刚刚那句话"，而是整个对话历史（或其中最近的部分）。 模型"看到"你的新问题 + 之前的对话 + 系统提示 = 这全部就是 Context。

⚠️ Context Window（上下文窗口）= 模型一次最多能"记住"多少 Token。 GPT-3 的窗口是 2048 token，GPT-4 Turbo 扩展到 128K。当对话超过窗口，模型就会"失忆"—— 你之前说过的话被裁剪掉，模型完全不知道发生过什么。这是当前 AI 最核心的限制之一。
📝

Prompt——你怎么跟AI说话，决定了它怎么回答

第 4 章

System Prompt（系统提示）

在对话开始时，开发者预先设定的规则。它定义了 AI 的"角色"、"风格"和"限制"。用户看不到它，但 AI 始终遵守。

例："你是一个专业的法律顾问，用通俗易懂的语言解释法律知识。不要提供具体法律建议。"

User Prompt（用户提示）

你每次输入的内容。这是你直接和 AI 对话的部分，叠加在 System Prompt 之上。

例："我和邻居因为围墙高度发生了纠纷，我该怎么办？"

Prompt Engineering（提示工程） 本质上就是设计 System Prompt 和 User Prompt，让 LLM 在有限的 Context Window 内产出最有效的回答。 好的 Prompt：明确角色、提供格式要求、给出思考步骤（Chain-of-Thought）、限制输出范围。

🔧

Tool Calling——AI 不再是"嘴炮"

第 5 章

LLM 只会生成文字——它不会查天气、不会算精确的日期、不会爬网页、不会写文件。 Tool Calling (Function Calling) 让模型可以"调用外部工具"。

1

用户问："今天上海天气怎么样？"

LLM 判断：我无法回答，但我有一个 get_weather 工具可以用。

2

LLM 返回工具调用请求

不是文字回复，而是一个结构化的 JSON：{"function":"get_weather","arguments":{"city":"上海","date":"2026-05-31"}}

3

程序执行该函数，把结果返回给 LLM

get_weather 函数被调用 → 返回 "上海今天晴，22-28°C"

4

LLM 用工具结果生成最终回答

"根据最新数据，上海今天天气晴朗，气温22到28摄氏度，非常适合出行。"

🔑 Tool Calling 是 LLM 从"聊天机器人"进化到"Agent"的关键一步。有了工具，AI 就不再只是说话——它可以行动。
🔌

MCP——工具的"USB 协议"

第 6 章

每个 LLM 平台（OpenAI、Google、Anthropic）的 Tool Calling 格式都不一样。开发者每换一个模型就得重新适配——直到 MCP (Model Context Protocol) 出现。

MCP 由 Anthropic 提出，是一个开放的、标准化的协议，让 AI 应用和外部工具之间用一个统一的"语言"通信。 类比：USB — 不管你是什么设备，插上去就能用。MCP — 不管你的工具是什么，AI 都能理解怎么调用它。

没有 MCP 时

每个工具都要为每个模型单独写适配代码。n 个工具 × m 个模型 = n×m 种适配。

有了 MCP

工具只需按 MCP 标准暴露接口，所有支持 MCP 的 AI 都能直接使用。n + m 种关系。

🤖

Agent——LLM + 工具 + 自主规划

第 7 章

Agent（智能体）= LLM + 工具 + 自主规划 + 循环执行。 它不是"一问一答"，而是"给一个目标，自己去想、去查、去做、去检查、去修正"。

1

感知 (Observe)

读入用户目标和当前状态。"我需要帮用户订一张从北京到上海的机票。"

2

规划 (Plan)

拆解任务：①查航班 → ②比较价格 → ③选最优 → ④确认 → ⑤下单。"每一步需要什么工具？"

3

执行 (Act)

调用工具：搜索航班 API → 获取价格列表 → 筛选 → 展示给用户确认 → 调用支付/预订 API。

4

反思 (Reflect)

"搜索失败了 → 换一个搜索引擎。价格不在预算内 → 换一个日期。用户拒绝了我的建议 → 重新搜索。"

Agent 和普通 Chatbot 的区别：Chatbot 是"我问你答"，Agent 是"我告诉你目标，你自己看着办"。 Agent 会自己拆任务、选工具、试错、重试——它有一个闭环。
🎯

Agent Skill——让 Agent 从"能干"到"擅长"

第 8 章

Agent Skill（Agent 技能）是把 Agent 的某项能力打包复用的概念。 一个 Agent 可能有多个 Skill——"搜索 Skill"、"订票 Skill"、"代码审查 Skill"。

Skill = 知识（这个任务该怎么做）+ 工具（需要哪些 API/函数）+ 流程（先做什么后做什么）+ 检验标准（怎么判断做完了、做好了）。

实际例子 — Claude Code 的 Skill： 一个"创建新页面"的 Skill 包含：(1) 知道页面的设计系统规范，(2) 能读写文件，(3) 先规划再写代码的流程，(4) 写完要测试验证的标准。 用户只需说"创建一个关于 XYZ 的新页面"，Agent 就自动执行整个 Skill。

"AI 发展的方向不是更大的模型，而是更自主的 Agent。Agent Skill 是让 Agent 从'一次性的任务执行者'变成'可复用的能力单元'。" — 马克的技术工作坊
